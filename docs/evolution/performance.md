# Native performance evidence

Performance acceptance remains open. Five alternating baseline/enabled pairs completed against the fixed [acceptance budget](performance-budget.md), but timing and resident-memory differences were smaller than the observed run spread. A separate lifecycle workload completed all 28 cycles and collected all 46 scoped retired objects. Reconnect resident growth exceeded the investigation threshold. A native-only control reproduced substantial growth with the LuaBuddy runtime absent. These results establish no budget pass or precise incremental loader cost.

The measured product image is optimized Linux x86_64 runtime SHA256 `832d2d869d648a5bd304e03831df6eca4ce78543301efceabab962141ff0178c`. The actual host was Project Zomboid `42.22.2`, revision `3d39148846`, bundled Zulu Java `25.0.5+8-LTS`, and Mesa `26.2.6` llvmpipe on a 24-CPU Linux host. Every arm used 1280×800, the same private cache and native launch settings, a vanilla loopback server with 4 GiB heap, empty native Mods/Workshop lists, checksum checking, and an ordinary player at `[10720.5, 10195.5, 0]`. The stationary indoor scene included the same native character and chat panels. The normal `showSurvivalGuide=false` preference was fixed in every disposable arm before deciding measurements.

The paired workload used 30 seconds of warmup and 30 seconds measured per run. All ten native start/end gates and normal native exits passed. Baseline clients had no LuaBuddy namespace; enabled clients had the runtime ready with zero selected profiles. All clients had zero native mods. The dataset contains 3,996 completed presentation intervals, with 1,962 baseline and 2,034 enabled intervals. Independent checks matched every reported interval array to its selected Mesa rows and confirmed that each interval sum matched its measured window. The host launch input and all private fixture file hashes remained unchanged.

The five-percent startup/p95, ten-percent p99, and 64 MiB resident-memory limits were not changed. The favorable frame-time medians do not establish a speedup. The startup and resident-memory point estimates also cannot establish a repeatable regression from this noisy dataset. End-of-run load observations ranged from 29.26 to 42.57 on 24 CPUs, despite other owned clients and builds being stopped. A separate unmeasured fixed-world profile, taken during the initial two-profile warmup of a setup attempt later rejected for UI navigation, attributed about 9.24 CPU cores to llvmpipe, about 0.38 core to C2 compilation, and 0.004 core to the readiness worker; llvmpipe threads often spent 30 to 38 percent of the sample waiting for CPU. Software rendering and host contention limit this workload. The protected running game was left untouched.

The observer uses Mesa Gallium's native `frametime` query. Installed Mesa computes wall time since the preceding renderer frame, writes each value to a line-buffered file, and continues collecting when the HUD is hidden. `GALLIUM_HUD_PERIOD=0` requests per-frame updates. Boundary row counts select consecutive intervals after warmup. These semantics were checked against the [Mesa environment-variable reference](https://docs.mesa3d.org/envvars.html#gallium-hud-period) and exact [26.2.6 source archive](https://archive.mesa3d.org/mesa-26.2.6.tar.xz). Both arms used identical instrumentation. A VM-managed daemon reads existing native UI/world state with fresh JNI local frames. The observer requests no breakpoint capability, changes no Java code or fields, and enables no global method tracing. Its common instrumentation cost was not independently isolated; the measured worker CPU figure does not quantify the complete HUD cost.

CPU and RSS come from the exact owned JVM's `/proc` records, using the actual host page size and clock tick frequency. Startup ends at an observed alive player in native `IngameState`, with exact account, viewport, role, profile/native-mod counts, and expected runtime presence. The same state is verified at the end, including the unchanged player position. Native UI visibility and completed work are required; an agent-load message or a file alone is insufficient.

The lifecycle workload used two owned test-content profiles and one JVM. It performed 11 no-op refreshes, 11 cooperative reloads, and six native reconnects, discarding the first cycle of each kind to leave 10, 10, and five measured samples. Every operation completed through native controls. The native log contains exactly 11 Refresh, 11 Reload, and seven startup operations, including the initial connection. After each operation and world resume, both real callback counters advanced from their recorded baseline. Shared generation IDs were checked for replacement and preservation without assuming adjacency. Native callback counts stayed at one owned and one foreign callback.

Temporary JNI identity references were cleared before one explicit GC request on the next poll. A fixed five-second settling interval preceded two seconds of RSS samples at 250 ms spacing. Heap used/committed bytes and weak-reference collection were recorded separately. Reload probes cover the replaced owned callback and its exported `LuaBuddyGrowth` table. Reconnect adds the old LuaBuddy namespace and foreign callback. All 46 retired probes were collected. The foreign module table, every JNI registration, and all native allocations were not weakly tracked.

Committed heap stayed at 3072 MiB in both reconnect scenarios. The native-only diagnostic used the same game/JVM, renderer, viewport, account, server, fixed scene, and GC/settle/sample policy. It loaded neither the product agent nor test profiles. A bounded map observation of its exact owned process showed the observer mapped and the product runtime absent. Each reconnect required an observed native menu transition, a new native Lua environment, the resumed ordinary player, zero namespace/profiles/native mods, and positive completed Mesa rows. It completed six raw cycles, discarded the first, captured 405 resumed-world frames, collected all six retired native-environment probes, and exited normally.

The native-only control demonstrates that substantial resident growth occurs without LuaBuddy. Its fresh-JVM history omitted the preceding Refresh/Reload operations, and the trends were not interleaved. Subtracting their difference would not establish incremental loader cost. Allocation attribution remains unresolved, and scoped object collection does not prove absence of every heap/native retention path. The process-growth investigation and noisy paired comparison therefore leave performance acceptance open.
