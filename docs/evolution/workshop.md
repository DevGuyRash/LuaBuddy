# Workshop adapter and activation evidence

The Rust Workshop adapter is implemented in `crates/luabuddy-host/src/steam.rs`. It attaches to the game's existing Steam context and exposes search, details, subscribed-item enumeration, subscription changes, downloads, progress, installed paths, and item-state observations. It never initializes or shuts down Steam and never runs, drains, or replaces Steam's callback queue. These operations need the host's ordinary callback loop to keep running.

The adapter currently enables its native ABI only on Linux x86_64. Other platforms return an unsupported-platform error. Windows and macOS runtime behavior has not been verified. The selected interfaces are the actual host's `SteamAPI_SteamUGC_v021` and `SteamAPI_SteamUtils_v010` exports. Interface pointers, the current Steam user handle, and application ID 108600 are checked on the owner thread before operations. The adapter opens an already loaded library with `RTLD_NOLOAD`; it cannot activate native code from a downloaded Workshop folder.

## Operations and safety

`SteamWorkshop::attach_existing` checks the game's native Steam-mode API before accessing the shared library. `start_search` and `start_details` return owned `Query` values. `Query::poll` checks only that query's Steam API-call handle through `IsAPICallCompleted` and `GetAPICallResult`. A query releases its UGC handle once on completion, cancellation, timeout, error, or drop. At most eight queries may be outstanding. Results retain Workshop identity, title, description, tags, dependency item IDs, update time, known size, and observed Steam state. Unavailable, banned, and foreign-application results appear separately in `SearchResults.unavailable`, with their index, returned item identity when present, and native failure metadata. One such result does not hide healthy rows. Invalid query handles, overall callback results, and incompatible native layouts still fail the query. Workshop child IDs are delivery dependencies; the game adapter must still inspect installed mod metadata for actual mod IDs, version restrictions, and load ordering.

Subscription and download writes require a matching item-scoped `UserIntent`. The in-game action that obtained that intent owns authorization. Native extension installation requires its own separate consent. Subscribing to unrelated Workshop content does not authorize executing native libraries. The initial verification was read-only. The user later authorized a real subscription/download test and asked the agent to choose its item. That follow-up uses one item whose original state was verified as not subscribed and not installed; the isolated symbol/JNI proof still performs no account operation.

Subscription requests retain their own API-call handle, consume acknowledgment once, and keep polling until the requested subscription bit is confirmed or the original deadline expires. Downloads use the existing private native `SteamWorkshop.n_DownloadItem(JZ)Z` requester on the game's exact system-loader instance. Its method shape is checked before use. This preserves the host's active-download bookkeeping and single-request rejection instead of bypassing it through the flat SDK download function. Java exceptions are cleared and returned as failures. Download tickets still require a fresh successful native completion callback, installed state, and a native install folder before reporting readiness. The JVM adapter in `download_events.rs` verifies the defining classloader, descriptors, and bytecode fingerprints of the game's existing `SteamWorkshop.onItemDownloaded` and `onItemNotDownloaded` methods before observing their entry. It records the native result and observation time without changing the callback body or taking over Steam's callback loop. The owner-thread ticket consumes only notifications observed after its request began. Download requests fail before calling the host when those verified observers or the native requester are unavailable. A timeout remains unconfirmed and is never labeled cancellation or success. Synthetic callback proofs and actual account download tests are separate evidence.

Steam's item API does not offer cancellation of one accepted download or subscription change. Closing an observation ticket stops LuaBuddy's observation while Steam may finish the request. `cancel_download` returns that limitation explicitly. Search cancellation releases only the owned query. Subscribed, installed, downloading, pending, and needs-update bits remain distinct. Enabling a profile and loading it in the running Lua environment are separate core/runtime operations.

## ABI evidence

Valve documents the [UGC operations](https://partner.steamgames.com/doc/api/ISteamUGC) and [API-call polling](https://partner.steamgames.com/doc/api/ISteamUtils). Its [UGC021 header in Proton's Steamworks SDK 1.62](https://github.com/ValveSoftware/Proton/blob/proton_11.0/lsteamclient/steamworks_sdk_162/isteamugc.h) supplies the current ABI declarations, including the additional subscription-enumeration boolean and trailing total-content-size field that older web documentation omits. The packed-four UGC result occupies 9772 bytes, with the total-size field at offset 9764. The installed Linux game's `libZNetJNI64.so` independently corroborates callback 3401 and its 280-byte result, the 12-byte subscription result, and several UGC field offsets. Its `CCallResult<SteamUGCQueryCompleted_t>::GetCallbackSizeBytes` returns `0x118`. Its query construction stores callback ID `0xd49`. Its `GetQueryUGCResult` implementation reads the title at offset 24, creation time at 8164, file size at 9484, and child count at 9760. The adapter's layout tests check the header layout and those independently observed offsets. Static layout evidence does not replace a live completed query.

## Reproduce the isolated host proof

Set `PZ_GAME_DIR` to the installed game root containing `projectzomboid.jar` and `natives`. The proof resolves the current host's 23 required flat Workshop symbols without invoking account APIs. Production lookup and proof coverage use the same export-name declaration. The proof creates a disposable JVM with the actual game JAR, verifies the private native download method and exact defining loader, and checks that native Steam-mode checks reject access before Steam initialization. An isolated Rust native test double on the existing method verifies argument routing, rejection, and Java-exception conversion. It never invokes the game's downloader or a Steam account operation.

```sh
JAVA_HOME="$PZ_GAME_DIR/jre64" cargo run --locked --offline --manifest-path proofs/steam/Cargo.toml -- "$PZ_GAME_DIR"
cargo test --locked --offline --manifest-path proofs/steam/Cargo.toml
```

The initial build needs the lockfile's declared Cargo dependencies in its cache. A normal Cargo fetch is a development dependency operation. The installed product does not download crates or invoke a compiler.

The initial November 9, 2026 symbol and unavailable-context proof passed against the installed Linux x86_64 game and its bundled Java 25.0.5. The aggregate repository baseline reports game 42.22.2, revision `3d39148846`. Adapter checks cover ABI layout, distinct subscription/install states, invalid result strings, item IDs and action intent, deadline overflow, missing-library refusal, per-item native failures, incompatible success layouts, and request-time-scoped notifications. A separate owned graphical client completed public title search and subscribed-item detail pages through the actual initialized Steam context. One native result 15 appeared as an explicit unavailable row while healthy rows and later pages remained usable. That real mixed-page check preceded the focused new failure tests. The isolated symbol proof alone does not establish those live operations.

The later authorized Steam-launched test used Item Condition Overlay, Workshop ID `3641048285`, with a disposable cache and profiles. From verified not-subscribed/not-installed state, one **Add / download** action confirmed the subscription and reached **Installation verified** through a fresh native success notification plus installed-state/path verification. This first successful journey used runtime SHA256 `b48e1c922061f6eab37f066568afb838558e793e074ed6e3afba3e83a391b509`. The same fresh-state journey then passed again on the reproducible Steam-tested runtime SHA256 `17ffaedb4f2d0a59002a536e408f53628d3a6d9d2b47f6b18a8b07951205c64a`. The earlier attempts exposed delayed subscription-state convergence and the game's required downloader bookkeeping; the adapter fixes and focused native/JNI checks address those failures.

Installed discovery resolved mod ID `ItemCondition_KingEJ`, version `1.3.1`, native minimum version `42.0`, and no required dependencies. A private profile selected that ID and opted into mounting its upstream texture. No bundled integration or mod file was changed. Joining a disposable Steam-mode server loaded both upstream client Lua files with no initialization error. The server retained empty native Mods/WorkshopItems, checksum and anti-cheat checks, and an ordinary user role. Actual inventory controls attached a native axe to Back, displaying its three condition bars in the hotbar; a bottle displayed its inventory fill bar. The upstream hotbar-size preference of 125 survived an ordinary Steam restart. Two **Load new profiles** actions each reported zero new profiles and retained the same loaded generation. A normal menu/reconnect restored the player, axe overlay, saved scale, and both source files in a distinct native Lua environment.

This establishes delivery and the exercised client behavior of that item on the tested Linux host. It does not establish every Workshop item, every upstream feature, a real update to newer content, safe cooperative reload for this mod, native extension activation through subscription, or a performance budget pass. Performance is recorded separately.

Cleanup restored the test item's initial unsubscribed/uninstalled state. One item-scoped production-adapter unsubscribe request ran on the actual `GameWindow.gameThread`, confirmed its acknowledgment and false subscription bit, and released its handles there. A later read-only ordinary restart observed both bits false after Steam removed its managed folder. No Workshop file was deleted manually. Private Rust instrumentation verified the exact system-loader method and Java thread object, preserved the host method body and callback pump, and cleared its own breakpoint. The accepted cleanup clients exited normally. An earlier read-only full-game attempt with extra JNI checking was rejected for upstream native warnings and performed no account write; it remains separate from the normal-flags accepted journeys.

## Native activation and one-click target

The inspected game Workshop path discovers installed mod directories and mounts their files. It has no inspected metadata action that activates a delivered Rust library as a JVM agent. A native library present in a Workshop item therefore establishes delivery only. An actual clean subscribe, ordinary launch, offline relaunch, update, and removal sequence has not established subscribe-only native activation.

The real Linux launcher supports a complete `ProjectZomboid64.site.json` override. An initial disposable probe established site-file selection before starting the game. The final installed-launcher journey then used the copied real executable, installed package, and private game-user directories. It reached native Options and invoked the Rust diagnostics callback after clean installation, offline relaunch, update, and rollback. Uninstall restored a native launch without LuaBuddy. User selections, saved preferences, and an unrelated JVM flag survived. This establishes the extra installer activation step, while subscribe-only Workshop activation remains unmet. Later changes to Steam's base configuration still require the installer's reconciliation and repair checks.

The later user-authorized normal installation preserved all 24 existing selections and migrated 16 recognized legacy hook profiles. It retained the original Lua files and recovery copies and left the base launcher JSON and executable unchanged. The normal Steam process mapped the installed `17ffaedb` Rust runtime, and fresh diagnostics completed with 24 loaded profiles and zero failed, pending, or restart-required profiles. Installation verification and `doctor` passed. This establishes activation through the installer for that normal launch; it does not establish subscription-only activation.

The later test-only portability correction produced runtime `1d44f599`. Its package passed two-path reproducibility and the native aggregate, and it is installed for the next normal Steam launch. The update preserved all current profile files. The running game remained on `17ffaedb` without interruption. The real subscription/download journey and normal 24-profile startup above retain their `17ffaedb` scope; neither was rerun on `1d44f599`.
